# 反编译工具链 + 官方转换主程序：融合工作流

可以融合，而且最稳的融合方式不是“二选一”，而是分层：

- `python-toolkit/` 负责 **生成新的 `.rob` 动作组**
- `wondercode-toolkit/` 负责 **用官方转换风格的 Python 主程序调用这些动作组**

这条路线的核心优点是：

1. **保留已验证资产**：你已经试过的反编译 / 编舞 / 安全审计工具链继续用。
2. **保留官方入口**：设备端仍然走 `Hiwonder.startMain(...)` 和 `tonybot.runActionGroup(...)`。
3. **能力互补**：官方路线擅长“调用”，反编译路线擅长“造新动作组”。

## 一句话理解

> 先用 `python-toolkit` 造出新的 `N号xxx.rob`，再在官方转换出来的主程序里 `tonybot.runActionGroup(N, 1)` 调它。

## 为什么这样最合理

当前两条路线的边界已经很明确：

### `wondercode-toolkit/` 的能力

- 优势：对齐官方积木导出结果，主程序、BLE、UART、流程控制块的落地写法明确。
- 限制：默认只能调用设备里已经存在的动作组编号。

### `python-toolkit/` 的能力

- 优势：可以从官方动作段、预设模块、手写帧编译出新的 `.rob`。
- 已验证项：`.rob` 结构、`EYPT`、安全审计、编舞 JSON 工作流。
- 关键产物：`动作/<编号>号<名称>.rob`

所以融合后的职责分工应当是：

| 层 | 仓库路径 | 职责 |
|---|---|---|
| PC 端生成层 | `python-toolkit/` | 生成、审计、导出新动作组 |
| 设备端调用层 | `wondercode-toolkit/` | 用官方转换风格的 Python 主程序触发动作组 |

## 融合步骤

### 1. 在 `python-toolkit/` 里生成新动作组

例如你已经有这些可直接部署的动作：

- `python-toolkit/动作/159号自制舞蹈.rob`
- `python-toolkit/动作/163号电摇.rob`
- `python-toolkit/动作/165号工业校歌逐拍精细版.rob`

如果要新建一支舞：

```powershell
cd python-toolkit
uv run python dance_workflow.py build "编舞\159号自制舞蹈.json"
uv run python rob_safety.py "动作\159号自制舞蹈.rob"
```

合格标准仍然是：

- Python 语法检查通过
- 安全审计 `violations=0`

### 2. 把 `.rob` 部署到设备动作存储区

这一层不在当前仓库里自动完成，但逻辑很简单：

1. 你在 PC 端得到 `159号自制舞蹈.rob`
2. 把它放进设备动作存储区
3. 设备端把它识别为动作组 `159`

> 这里最关键的是：**设备里的动作组编号必须和 `.rob` 文件编号一致。**

### 3. 在官方转换风格主程序里直接调用

部署后，设备端不需要知道这个动作是“官方原厂”还是“你自己编出来的”，调用方式完全一样：

```python
tonybot.runActionGroup(159, 1)
tonybot.waitForStop(20000)
```

只要设备里真的存在 `159` 号动作组，这和调用 `0`、`9`、`49`、`50` 没有本质区别。

## 已确认的交叉验证结论

通过 `python-toolkit/文档/07-动作库目录.md`、`python-toolkit/main.py` 和官方转换样例交叉对照，当前能确认：

1. `runActionGroup(N, x)` 的第一个参数 `N` 就是动作组编号。
2. 原厂动作号如 `0`、`9`、`10`、`49`、`50` 可以直接调用。
3. `python-toolkit/` 生成的新 `.rob` 只要按编号部署到设备，也可以同样被直接调用。

## 需要特别注意的编号语义

这里最容易混淆两类编号：

### 原厂动作号

例如：

- `0` 立正
- `9` 挥手
- `10` 鞠躬
- `49` 原地踏步
- `50` 扭腰

这些通常是设备原本就有的。

### 你的自定义动作号

例如：

- `159号自制舞蹈.rob`
- `163号电摇.rob`
- `165号工业校歌逐拍精细版.rob`

这些不是“官方默认一定存在”的动作号，而是 **你生成并部署后才存在**。

### 语义模块号

例如：

- `303号礼貌鞠躬`
- `308号标准踏步`
- `312号扭腰单拍`

这些是 `python-toolkit/` 里的工具链语义模块编号。它们只有在你真的把对应 `.rob` 以这个编号部署到设备后，设备端才能直接 `runActionGroup(303, ...)` 调到。

## 最推荐的实际用法

### 方案 A：主程序里只写最终编号

这是最稳的设备端写法：

```python
tonybot.runActionGroup(159, 1)
tonybot.waitForStop(20000)
```

优点：

- 设备端逻辑最简单
- 完全贴合官方调用方式
- 适合比赛、展示、量产脚本

### 方案 B：PC 端持续迭代，设备端编号固定

这更适合反复调舞蹈：

1. 约定某个编号专门给测试舞蹈，例如 `159`
2. 每次都用 `python-toolkit` 重建新的 `159号测试舞蹈.rob`
3. 重新部署到设备
4. 设备端代码保持不变：

```python
tonybot.runActionGroup(159, 1)
```

这样你只换动作文件，不换主程序。

## 当前建议

如果你更信任之前已经试过的反编译路线，那么后续默认策略应当改成：

1. **动作内容** 一律优先在 `python-toolkit/` 里生产和验证
2. **设备端主控** 一律优先参考 `wondercode-toolkit/` 的官方转换风格
3. 两边通过“动作组编号”做桥接

这就是当前最稳、最少假设、最容易继续验证的融合方案。
